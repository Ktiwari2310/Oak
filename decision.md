# Backend Decisions

This document records the backend design choices reflected in the current Oak implementation. It describes the implemented state and calls out decisions that remain deferred.

## Platform and persistence

- The service is a Java 21 Spring Boot 4.1.0 REST API. Spring MVC exposes HTTP endpoints, Spring Data JPA provides repository access, and Jakarta Persistence maps the entities.
- The application process uses UTC so JDBC startup and persisted timestamps do not depend on host-specific timezone aliases.
- PostgreSQL is the configured application database. H2 is included for tests.
- Hibernate schema management is configured with `spring.jpa.hibernate.ddl-auto=update`; this updates the existing schema but should not be treated as a substitute for reviewed production migrations.
- Entity relationships are represented with JPA associations. Controllers resolve submitted related-entity IDs through repositories before creating or changing relationships.

## API contract

- Resource routes use `/api/...` paths and preserve their established HTTP methods.
- Successful responses use the `ApiResponse<T>` envelope with `message` and `data`.
- Create operations return HTTP 201. Reads, updates, and deletes return HTTP 200 on success.
- Request bodies use dedicated records in `com.oak.request`, rather than accepting persistence entities. Bean Validation checks request fields, and controller mapping selects which fields can be written.
- Response DTOs in `com.oak.response` isolate API output from entity serialization. JSON property names are camelCase.
- Resource lookup failures use a not-found exception and a common 404 response. Invalid references and request validation failures return 400; database integrity conflicts return 409. Unexpected errors return a generic 500 response without stack details.

## Domain choices

- Users own repositories and can post issues and comments. Issues belong to a repository and have a poster. Comments belong to an issue and a poster.
- Labels belong to repositories. `IssuesLabels` represents the issue-to-label association. Pull requests link an issue with head and base repositories.
- IDs are generated by the database and are not accepted in request DTOs. Public identifiers for relationships are passed as IDs, then resolved before persistence.
- New API-created users are assigned `is_admin = false`; clients cannot set administrative status through the create request.
- The `issues.index` database column is retained and quoted in the JPA mapping to avoid a schema rename.
- Database uniqueness protects usernames, email addresses, repository names per owner, label names per repository, issue numbers per repository (using the existing `index` column), and issue-label pairs.
- Issue numbers are assigned as the repository's current maximum plus one. Issue creation locks its repository row while reading and saving the number so concurrent creates for that repository do not select the same next number.
- A label can only be attached to an issue from the same repository. A pull request cannot target the same repository and branch on both sides.
- Comment types are stored as enum names: `COMMENT`, `REVIEW`, `CLOSE`, `REOPEN`, and `MERGE`.
- User passwords submitted as plain `password` request fields are hashed with BCrypt before persistence. Password hashes are excluded from response DTOs and must not be logged.
- Global CORS applies to `/api/**`; allowed origins are configured as a comma-separated `app.cors.allowed-origins` property, not as a wildcard on an individual controller.
- All unfiltered `findAll` collection endpoints are paginated with Spring Data `Pageable`, defaulting to 20 items per page; page metadata is returned within `ApiResponse.data`.
- Entity creation/update timestamps are managed by Hibernate (`@CreationTimestamp` and `@UpdateTimestamp`), rather than client input or `LocalDateTime.now()` field initializers.
- Deleting a repository removes its issues and labels; deleting an issue removes its comments, issue-label links, and pull request. Parent-side collections are JSON-ignored to avoid exposing persistence graph internals.
- User deletion does not cascade. A user with owned repositories, posted issues, or comments is still referenced by foreign keys and cannot be deleted until those dependents are handled. Repository deletion removes that repository's issues and labels, but does not delete their posters or commenters.

## Deferred decisions and safeguards

- Authentication and authorization are not implemented. Repository privacy therefore cannot yet be enforced per caller; read paths carry TODOs and must not be treated as protecting private repositories until authentication is added.
- Existing duplicate database values may prevent new unique constraints from being installed through `ddl-auto=update`; clean or migrate such data before applying the constraints in an existing database.
